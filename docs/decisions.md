# 設計判断の記録

作成：2026-11-06。状態はすべて「モックとしての判断」。本番方針ではない。

## D1. GPT-Liveの接続方式：WebRTC＋サーバsideband＋client delegation
- 確認した公式情報（2026-11-06、openai npm 7.53.0の型定義と公式ガイド）
  - モデルID `gpt-live-1`。WebRTCは `POST /v1/live/sessions`（SDK `client.live.create`）でサーバがSDPを交換。エフェメラルキー方式はGPT-Liveのガイドに記載なし。
  - sideband：`wss://api.openai.com/v1/live/sessions/{id}/attach`（SDK `SidebandWS`）。
  - client delegation：`session.delegation.created` は委任の通知であり、ユーザー発話のテキストもターン完了も含まない。結果は `session.thinking.append` / `session.commentary.append` / `session.instructions.append`（各500 tokens上限、`delegation_id`必須・nullable）。
  - transcript：`session.input_transcript.delta` / `session.output_transcript.delta`（start_ms/end_ms）。確定ターン完了イベントはない。
- 判断：業務状態はサーバが単独で持つため、transcript受信と指示送信はsideband（サーバ）で行う。ブラウザは音声とミュート/終了のみ。
- Realtime API（`/v1/realtime/calls` 等）のイベントとは別物として `server/src/live/liveAdapter.ts` に隔離。

## D2. 委任されていない分析結果は「話させない」
- transcriptのgapでも分析を走らせ、事実と状態を最新化する（委任を待つと状態更新が遅れるため）。
- ただし委任されていないときの通常の質問案は `thinking`（無音の背景情報）として渡し、GPT-Liveの自発発話と二重にならないようにする。
- 例外：読上げ確認・転送・緊急・登録結果など、ゲート済みで文言が決まっている案内は `instructions.append` で「そのまま伝える」よう指示する。
- 要検証：instructionsで文言どおりに話すか、言い換えや省略が起きるか（[S4] 事後監視だけでは発話を物理的に防げない）。

## D3. 読上げ確認の「出力済み」判定はヒューリスティック
- テキストモード：表示時点で出力済み。
- 音声モード：読上げ指示の受理（`session.instructions.appended`）後のAI出力transcriptが読上げ文の50%以上の長さで「確認」を含む場合に出力済みとする。**要検証**。
- 出力済みでなければ「はい」を同意として記録しない（ActionGate）。

## D4. 振り分けと権限はコード、会話の順序はLLM
- `decideRoute`（コード）：緊急 > レッカー > 有人希望 > 明確な非対象 > 未確認 > 対象。未確認をfalseにしない。
- `ActionGate`（コード）：確認準備・同意記録・登録提出・完了案内・契約開示。
- LLM Brainは次の会話目的と発話案を選ぶ。コードは不足項目の集合と制約だけを渡し、固定の next_field を返さない。
- 自動完結の事案種別は allowlist（`collision` のみ）。当て逃げ・故障・盗難等は対象外。

## D5. Deterministic比較モード（RuleBrain）を併設
- 既存リポジトリがなく「既存Deterministicモード」は存在しなかったため、比較用・APIなし回帰テスト用に新設。
- これは固定順の質問をする（＝過去モックのIVR的方式に相当）。LLM方式との比較対象として残す。
- キーワード規則のため、自由な言い換えへの頑健性はない。業務ロジック（ゲート・状態遷移）のテストに使う。

## D6. 世代管理と後着結果
- 分析は会話ごとに直列化。各分析に `analysisId`・`baseStateVersion`・`inputWatermark` を付与。
- 適用時に版が変わっていれば破棄して再評価。タイムアウト後に届いた結果は `late_discarded` として記録のみ。
- 事実が変わると版を上げ、未同意の確認は失効。同意後の変更・QUEUEDジョブは取消して再確認。RUNNINGは停止要求→書込前停止なら再確認、書込済みなら訂正待ち（有人）。2件目の新規登録はしない。

## D7. RPA・基幹は模擬、形式はモック独自
- `mock-rpa-v0.1`。既存RPAの入力形式ではない。Mapperはコードで行い、LLMに列や形式を決めさせない。
- 冪等性：ジョブ台帳（同一idempotency_key）と模擬基幹台帳の両方で重複排除。Exactly-onceは保証しない。
- OUTCOME_UNKNOWN は自動再送しない。画面の「基幹台帳を照合」で同一キーの登録を回収。

## D8. 契約照会
- 架空契約2件。「2項目一致」は契約特定の基準として扱い、本人認証・開示許可とは別。モックは本人認証を実装せず、開示は常に不可。
- 契約未特定で事故概要が揃った場合は HANDOFF_PENDING → 有人引継ぎ（登録完了とは言わない）。

## D9. ホスティング：Render無料枠（Takaさん選択 2026-11-06）
- 常駐Nodeプロセス（SSE・模擬Worker・sideband WebSocket）が必要なためサーバレスではなくWebサービス。
- 外部公開のため `APP_PASSWORD` 必須（production で未設定なら起動拒否）。署名付きHttpOnly Cookie、ログイン試行のレート制限。
- 費用・負荷の上限：1通話の最大秒数、同時接続数、1日のセッション数、LLM評価の最大回数。

## D11. 物損（公共物・無人の駐車車両）をSTS対象に拡大（Takaさん決定 2026-11-06）

- STSで受け付ける：
  - 公共物（電柱・ガードレール・標識・信号機等）への接触：相手情報は聞かない。警察届出（`police_reported`）を聴取。`property_ownership=public`。
  - 人が乗っていない駐車車両への接触（`parked_vehicle_unoccupied=true`）：相手の名前・住所・電話番号と警察届出を聴取。
  - 相手情報・警察届出は「分からない」でも登録まで進める（`explicitly_unknown`）。登録データに `counterparty.contact_required=true` と、不明があれば `info_incomplete=true` を付ける。
- 有人のまま：人が乗った相手車（信号待ちの追突等）・走行中の相手車・歩行者・自転車、他人の塀・店舗の壁・借家（`property_ownership=third_party`）、当て逃げ、けが・レッカー・緊急・有人希望。
- 受入ケース：T05（電柱）を OPERATOR → SELF_SERVICE に変更し、警察届出の聴取と登録まで確認。T03 は「相手車に人が乗っていたか」を確認してから OPERATOR。T37（無人の駐車車両）・T38（人が乗った停車車両）・T39（駐車車両の持ち主不明）を追加。`requirements/acceptance-cases.json` は原本のまま残し、差分はここに記録する。
- D10の「警察届出」は、この範囲（公共物・駐車車両）に限り聴取する。届出の要否判定や案内はしない。

## D12. Live発話の調整（2026-11-06）
- 委任中のつなぎ言葉（「承知しました、確認しますね」）を言わないようにLive instructionsで指示。Brainの発話案にも毎回の前置きを付けない。LLM Brainの分析中（1回6〜8秒）は無言になる点は要検証。
- 委任なしの「そのまま伝えて」指示（転送結果の案内など）は、前の「そのまま伝えて」の発話が終わってから送る（発話が混ざる問題への対策）。終わりの検知は出力transcriptの区切りで行い、10秒で強制的に次へ進む（要検証）。

## D13. LLM Brainの応答時間と言い回し（2026-11-06 Takaさん実機フィードバック）
- 間が長い（gpt-6-luna で分析1回6〜8秒）→ Responses APIに `reasoning.effort`（環境変数 `BRAIN_REASONING_EFFORT`、既定 `low`）を渡す。モデルが受け付けない場合は初回エラー後に指定なしへ自動で戻す。効果は実機で要検証。
- けがの質問は一度だけ。「いない」なら全員分の回答とし、乗車人数は聞かない（本人だけの否定のときのみ同乗者を確認）。
- 安全の確認は「急いで対応が必要な状況はありますか」の趣旨で聞き、「煙・火など」の例示や「危険な状況」という言い方をしない。

## D14. 音声側に質問を作らせない（2026-11-06 Takaさん実機フィードバック「矢継ぎ早で話しづらい」）
- 事象：GPT-Liveが、バックエンドの質問に別の質問を付け足したり（「けがをされている方はいますか」）、委任の結果を待たずに自分で質問を作ったりして、質問が連続していた。
- 対策：
  - 話す内容は質問も含めてすべて `session.instructions.append`（そのまま伝えて）で渡す。言い換えの余地があった `commentary` は使わない。
  - 背景情報（thinking）から「未取得項目の一覧」を外し、「自分から話さない参考情報」と明記した。
  - Live instructionsに「届いた内容だけを話す・付け足さない・質問したら答えを待つ」を追加。Brainの発話案は質問1つに限定。
- 副作用（要検証）：言い回しが固定的になる。自然さはBrainの発話案の質で担保する。

## D15. つなぎ言葉と言い回し（2026-11-06 Takaさん実機フィードバック）
- 実測（CONV-8a152496）：顧客の発話終了から次の質問まで約6〜8秒。内訳は、発話の区切り検知 約1秒、LLM Brain（gpt-6-luna、reasoning low）3.4〜5.9秒、音声側が話し始めるまで 約1〜2秒。最大要因はBrain。
- 委任から `LIVE_FILLER_AFTER_MS`（既定2500ms）経っても結果が出なければ、「確認いたします。」とだけ言う。言い終わる前に届いた結果は、言い終わってから送る。
- 相づちは「はい」のみ（「うん」「ええ」は使わない）。名前は「カタカナで」と言わずに聞く。

## D16. 遅延改善のプロファイル（A/B/C）と、質問のコード選択（2026-11-06 Takaさん作業指示書「応答遅延改善」）
- 改善前の挙動を残したまま比べられるよう、プロファイルを3つ用意した。画面の「応答速度の構成」で通話ごとに選べる。既定は環境変数 `LATENCY_PROFILE`（未設定なら `hybrid`）。
  - A `baseline`：改善前（従来のLLM Brain。質問文もLLMが作る。委任時の待機あり）。
  - B `lightweight`：Brainは発話の理解（事実候補・危険信号・曖昧さ）に専念し、次の質問の順序と文言はコードが選ぶ（`server/src/domain/questions.ts`）。出力項目を減らした軽量スキーマ、直近12発話だけ渡す、静的な指示を先頭に置く（プロンプトキャッシュ）。委任時の不要な待機を削減（D18）。
  - C `hybrid`：B＋Fast Path（D17）。
- D4（会話の順序はLLM）をB/Cでは変更する。理由：質問文の生成が出力トークンの多くを占め、Brainの待ち時間の主因だったため。副作用：質問順が固定的になる（自然さは「事故の状況を自由に話してもらう」質問を早めに入れて補う）。
- コード選択の順序：レッカー → 一部だけのけがの否定・相手車の乗員の確認 → 「今、急いで対応が必要な状況はありますか」（1回）→ 「どのような事故だったか」（1回）→ 対象判定の不足 → 登録項目の不足。
- 曖昧な回答の聞き直しだけはLLMが質問を作る（`clarify_question`）。補償・有人希望などへの一言は `speech_prefix`（質問を含めない）。
- 対象確認の試行上限（6回）は、B/Cでは「何も進まなかった分析」だけを数える（質問が2つ増えたことで、進んでいるのに上限で有人転送になるのを防ぐ）。Aは従来どおり。
- 推論量：公式モデルページ（2026-11-06確認）で gpt-6-luna / gpt-6.1-terra は `none, low, medium(既定), high, xhigh, max` に対応、`minimal` の記載なし。比較は none / low / medium で行う。受け付けられない値は初回エラー後に指定なしへ戻す（従来どおり）。

## D17. Fast Path（定型の短い回答をLLMなしで確定）
- 対象は7問だけ（レッカー・急ぎの状況の「ない」・けが・相手の有無・駐車車両の乗員・警察届出・SMS）。直前にAIが実際に話した質問ID（コードが選んだ質問）と、発話全体の完全一致（許可リスト）の組み合わせでだけ確定する。「はい」「いいえ」を単体では解釈しない。
- LLMへ回すもの：否定＋別の内容、推量（〜と思います）、言い直し、相づち・ノイズ、未分析の発話が2件以上、質問が実際に話されていない、最終内容確認への返事（同意）、急ぎの状況への「はい」。
- 確定結果は通常のBrainと同じ ReceptionPlan として applyPlan に渡す（同じ状態管理・振り分け・ActionGate）。watermarkが進むので、同じ発話をLLMで二重に処理しない。けが・レッカーの「はい」は振り分けで有人/レッカー転送になる。
- Shadow評価（`FASTPATH_SHADOW=1`）：確定済みの発話を裏でLLMにも分析させ、一致/不一致を記録するだけ。確定済みの状態は書き換えない（後追いの非同期結果で状態を変えると不整合になるため）。API費用が発生するため既定はオフ。
- 適用率・LLMへ戻した理由（fallbackReason）をターンごとに記録する。

## D18. 応答遅延の計測と、委任時の待機の削減
- ターン（顧客の発話〜AIの次の発話の開始）ごとに turnId を付け、顧客の発話終了・委任受信・Fast Path・Brainの開始/終了・コード判定完了・発話指示の送信・最初の音声・応答の音声開始を記録する（`server/src/session/latency.ts`）。
- 「サーバが把握する音声開始」はGPT-Liveの時間軸（入力の end_ms と出力transcriptの start_ms）で比べる。応答の音声は、送った指示の event_id と出力transcriptの client_event_id で照合する（付いていなければ「送信後に始まった最初の出力」で近似）。
- 「利用者が実際に音を聞いた時点」はブラウザが音量の立ち上がりで測り、時間の値だけをサーバに送る（音声そのものは送らない）。近似値（要検証）。
- 記録するのは時刻・項目キー・理由コードだけ。発話本文や個人情報は新たに記録しない。会話ログと同じ保存期限（既定72時間）で削除される。
- 委任時の待機：従来は、委任が来た時点で未分析の発話がないと `LIVE_DELEGATION_WAIT_MS`（1.2秒）待っていた（委任が入力transcriptより先に届く場合への備え）。B/Cでは、そのターンの発話をすでに受け取って分析済みなら待たずに答える。発話をまだ受け取っていない場合は従来どおり待つ。
- `LIVE_TURN_GAP_MS`（900ms）は変更しない。下げると発話の途中で分析が始まりやすくなる。まず計測で区切り検知の実際の時間を確認してから判断する。

## D20. B/Cで委任が来ずに固まる件への対策（2026-11-07）
- 事象（CONV-cb163cbd、hybrid・LLM Brain）：レッカーの質問に「いいえ」と答えた後、AIが17秒間黙ったまま通話終了。
- ログから分かったこと：
  - Fast Pathが発話の区切り（transcript_gap）で即座に結果を出したが、その時点でGPT-Liveの委任（delegation.created）はまだ来ていなかった。
  - 委任前の結果は、従来どおり「参考（自分からは話さないこと）：次の質問予定は…」と会話メモをthinkingで送っただけだった。
  - その後、委任は最後まで届かず、自動の相づちもなかった。サーバは委任を待ち続け、何も話さなかった。
  - 改善前（A）はLLMが遅いため、ほぼ必ず委任が先に届き、この経路を通っていなかった。
- 原因の見立て（要検証）：委任より先に送ったthinking（とくに「自分からは話さない」「委任して結果を待つ」）が、GPT-Live側の委任・相づちを止めた可能性がある。ただし、以前の通話（CONV-8a152496）では委任前にthinkingを送った後も委任が届いており、確証はない。
- 対策（B/Cのみ。Aは従来どおりで、改善前の挙動を再現できる）：
  - (１) 委任より先に結果が出ても、thinking（質問の予告・会話メモ）は送らない。会話メモは保留し、応答を送った直後に送る。
  - (２) 見張りタイマー：結果が出てから `LIVE_PROACTIVE_AFTER_MS`（既定1.5秒）委任が来なければ、今の質問を「そのまま伝えて」で自分から話す。顧客が話している・AIが話している・分析中のときは話さない。
  - (３) 自分から話した後に遅れて委任が届き、その間に顧客の新しい発話がなければ、同じ質問を繰り返さず、委任には「すでに伝えた。黙って待つ」とthinkingで返して閉じる（GPT-Liveがこれで委任を閉じるかは要検証）。新しい発話があれば通常どおり分析して答える。
- 計測：自分から話したターンも「応答の送信」として記録するため、応答時間（total_ms）に含まれる。ログに `result_ready_before_delegation` と `proactive_answer_without_delegation` が出る。

## D21. 音声モデル gpt-live-1.1 を通話ごとに選べるようにする（2026-11-20）
- 背景：OpenAIが 2026-11-20 に gpt-live-1.1 をAPIで提供開始（OpenAI Developer Community の告知）。SDKは openai 7.61.0 でモデル候補に追加。
- 公式記載の変更点：文字・数字などの細部の聞き取り、指示への従い方、タスク完了の確実さが向上。話しながら聞ける。言語をまたいでアクセントと声が安定。数値の改善幅（遅延など）は未公表。
- 料金は gpt-live-1 と同じ $0.05/分。同時接続数の上限は gpt-live-1 と別枠。APIの破壊的変更の記載はない。gpt-live-1 の提供終了日の記載もない。
- 実装：画面の「音声モデル」で通話ごとに gpt-live-1 / gpt-live-1.1 を選ぶ。候補は `LIVE_MODELS`、既定は `LIVE_MODEL`（gpt-live-1のまま）。許可リスト外の値はサーバが既定に戻す。
- 比較のため、会話（live.model）・ターンの遅延記録（liveModel）・`live_session_created` ログにモデルを残す。`/api/metrics/latency` はモデル別に集計する。

## D22. 委任時の自動の相づち「はい」を止める（2026-11-20）
- 事象（CONV-e7924729、gpt-live-1.1・hybrid・LLM Brain）：「はいどのような事故だったか…」（A-11）、「はい。」だけの発話（A-14・A-20）、「は、はい」のような詰まり。
- ログから分かったこと：
  - 「はい」は、委任（delegation.created）の約200ms後に毎回出ている（TURN-2は委任18800ms→音声19000ms、TURN-3は30800ms→31000ms、TURN-4は46800ms→47200ms）。
  - これはGPT-Liveの自動の相づち。`delegation.acknowledgement_delay_ms` の既定が0（委任と同時に要求）のため。公式（SDK 7.62.0の型説明）では、commentary・thinkingを送ると未発話の相づちは取り消される。
  - Fast Pathで応答が即座に出るターンでは、相づち「はい」の直後に質問が続くため「はいどのような…」とつながる。LLMを待つターンでは「はい。」→「確認いたします。」→質問、と前置きが二重になる。
  - planned（送信予定）が同じ文で2件ずつ記録されているのは、委任前に決まった質問を委任時に送り直したことの記録で、実際に2回話したわけではない（live_sendは1回）。
- 対策（D23で修正）：`acknowledgement_delay_ms` を `LIVE_ACK_DELAY_MS`（既定8000ms）で指定する。応答と会話メモ（thinking）が先に届けば相づちは取り消されるので、通常は言わない。待ちが長いときは従来どおり自前のつなぎ言葉（2.5秒で「確認いたします。」）が出る。gpt-live-1にも同じ設定を使う（0で従来の挙動）。
- 要検証：gpt-live-1.1でも相づちが実際に止まるか。8秒を超える待ちで相づちとつなぎ言葉が重ならないか。

## D23. D22の修正：8000msで通話が切れた件（2026-11-20）
- 事象：D22をデプロイ後、「音声で開始」直後に通話が切れた。Renderで `LIVE_ACK_DELAY_MS=0` を設定すると直った（Takaさん確認）。
- 原因：`acknowledgement_delay_ms` の許容範囲は 0〜800ms（openai-cli PR #639 の記載）。8000は範囲外。公式のLive APIリファレンス本文での確認は未了（要検証）。
- 対策：
  - (１) 待ち時間は上限800msに丸める。既定は800ms。
  - (２) 公式ガイド（Delegation and tools in GPT-Live「Suppress automatic acknowledgments while tools run」）の方法で取り消す。thinking・commentaryを送ると、未発話の相づちはすべて取り消される。
  - 委任を受けてすぐ答えられないとき（LLM分析中・発話の取りこぼし待ち）だけ、委任IDを付けない短い会話メモ「バックエンドで確認中。何も言わずに結果を待つ。」をすぐ送る。委任IDを付けないのは、応答を送るまで委任を開いたままにするため。
  - Fast Pathで即答できるときは送らない（応答と会話メモで取り消される）。
  - `LIVE_ACK_CANCEL=0` で (２) を無効にできる。
- 要検証：実機で「はい」が止まるか。会話メモを委任直後に送ることで、D20のような沈黙が起きないか（D20で問題になったのは委任「前」のthinking）。

## D24. 送信予定（AI(予定)）の二重記録をなくす（2026-11-20）
- 事象：同じ質問が「AI(予定)」に2件ずつ表示される（Takaさん指摘）。実際の発話は1回。
- 原因：委任より先に決まった質問（Fast Path等）を、決まった時点（送らずに委任を待つ）と委任時（実際に送る）の両方で送信予定として記録していた。Baselineの「参考として伝える」だけの結果も同様。
- 対策：GPT-Liveに話させる指示を実際に送るときだけ記録する。判断の履歴は従来どおり監査ログの speech_directive に残る。

## D25. 古い分析結果で質問する・同じ質問を自分から繰り返す件（2026-11-20）
- 事象（CONV-ae842bd9、gpt-live-1.1・hybrid・LLM Brain）：「今日の」「22時です」と続けて答えたのに「何時ごろでしたか」と聞いた。その後、損傷の質問が顧客の発話と重なり、同じ質問を2回した。
- ログから分かったこと：
  - 顧客の答えが U-19「今日の」と U-21「22時です」の2つに分かれた（音声上の間は0.4秒だが、文字起こしの到着が1.3秒空いた）。
  - U-19だけで分析中に U-21 が届き、再分析待ちになった。委任も再分析待ちに入った。
  - U-19だけの分析結果（日付のみ）で「何時ごろでしたか」を決め、待っていた委任への応答として話した。
  - 再分析（U-21を含む）で時刻が埋まり、次の損傷の質問が委任前に決まった → 委任が来ないため1.5秒後に自分から質問（D20）。
  - その質問の途中で、顧客が「22時です」と言い直した（U-27）。「何時ごろでしたか」への答え。音声が重なり、GPT-Liveは質問の残りを言い直した（A-29）。
  - U-27の分析でも受付データは変わらず、同じ損傷の質問が再び決まり、自分から2回目を話した（A-31）。
- 対策：
  - (１) 分析中に顧客が続きを話して再分析待ちになったら、その分析で決めた質問・案内は話さない。再分析の結果で1回だけ答える。緊急・転送・確認の案内は止めない。ログ `stale_question_suppressed`。
  - (２) 自分から（委任なしで）話した質問と同じ質問に戻り、その後に受付データが何も変わっていなければ、自分からは繰り返さない。顧客が話して委任が来れば、そこで答える。ログ `proactive_repeat_skipped`。

- 要検証：実機で、(２)で黙ったまま進まなくなる場面がないか。

## D26. 証券番号の確認が繰り返される・氏名の読みが変わる件（2026-11-20）
- 事象（CONV-3e136996）：
  - 証券番号「C123456789」を伝えても契約が見つからず、同じ質問（証券番号か登録番号）を繰り返した。
  - 契約者氏名「キタガワタカトシ」が文字起こしで「北川隆司」になり、その漢字から読みを推測して「キタガワリュウジ」と記録した。
- 原因：
  - モックの契約DB（PolicyAdapter）には MOCK001／MOCK002 しかなく、C123456789 は一致しない。一致しない限り `policy_match` が不足のまま残り、同じ質問を選び続けていた。
  - 「Cの123456789」「シーの…」のような言い方は、表記がそろわないと照合できない。
  - GPT-Live の文字起こしは氏名を漢字にすることがあり、読みは漢字からの推測になる。
- 対策：
  - (１) 証券番号の表記をそろえる（`normalizePolicyNumber`）：全角→半角、「の」・区切り・「です」を除く、英字の読み（シー→C 等）を英字に。Brain の抽出ルールにも同じ指示を追加。
  - (２) 契約確認は同じ質問を繰り返さない（`policyQuestion`）：
    - ①1回目は証券番号か登録番号を聞く。
    - ②番号を聞き取ったのに見つからなければ、聞き取った番号を読み上げ（「C・123・456・789で承りました」）、もう一方の番号を1回だけ聞く。言い間違い・聞き間違いに顧客が気づける。
    - ③何も聞き取れなければ、言い方を変えて1回だけ聞き直す。
    - ④それでも確認できなければこれ以上聞かず、残りの項目を先に聞く。不足が契約確認だけになったら有人へ引き継ぐ。
  - (３) 氏名の読みが漢字からの推測（元の発話に漢字があり、カナの読みが含まれない）なら、次の質問の前に「お名前の読み方を、一文字ずつ区切って教えていただけますか」を1回だけ聞く。Brain には、漢字で聞こえた氏名は元の表現に漢字を残し、一文字ずつの読みが来たらカナにつないで訂正するよう指示。
- 対策しなかったこと：テスト用の契約（C123456789）をモックDBに足すこと。氏名などのテストデータは利用者に確認してから。
- 要検証：
  - 実機で、GPT-Live が「Cの123456789」をどう文字起こしするか（英字が「シー」「C」「し」のどれになるか）。
  - 読み方の確認を一文字ずつ答えてもらったとき、Brain がカナに正しくつなぐか。

## D27. 氏名の読みは一文字ずつ聞かず、GPT-Live の復唱で取る（2026-11-20、D26 (３) を置き換え）
- Takaさんの指摘：氏名は基本的に漢字で文字起こしされる。毎回「一文字ずつ区切って」と聞くと顧客体験を損なう。
- 前提：GPT-Live の API には、文字起こしの表記（カナにする等）を指定する設定がない（openai 7.62.0 の型定義で確認）。音声を聞いているのは GPT-Live だけ。
- 対策：
  - (１) 一文字ずつ聞く質問（D26 (３)）は廃止。
  - (２) 氏名の読みが漢字からの推測なら、次の質問を送るときに1回だけ、GPT-Live に「お客さまのお名前を聞こえた読みのとおりカタカナで『〇〇様ですね。』と確認し、続けて質問を伝える」よう指示する。顧客の追加の受け答えは不要（「キタガワタカトシ様ですね。折り返しのお電話番号を教えてください。」）。
  - (３) その発話の出力transcriptから「〇〇様」のカタカナを取り出し、氏名の読みとして記録する（ログ `name_reading_from_echo`）。以後、Brainが漢字から推測し直しても上書きしない（顧客の訂正だけ反映、ログ `name_echo_kept`）。
  - (４) 復唱が漢字などで文字起こしされ読みが取れなければ、推測の読みのまま（ログ `name_echo_unusable`）。最後の読上げで顧客が訂正できる。
- 要検証：
  - GPT-Live が聞こえた読みで正しく言えるか（文字起こしの漢字に引きずられないか）。
  - 出力transcriptがカタカナになるか（漢字になると(４)）。
  - 復唱の分、質問が1.5秒ほど長くなる。
